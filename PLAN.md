# План створення

## Узгоджені вимоги

Репозиторій: публічний `Cheewbacca/kyiv-alert-widget`. Перша версія лише для особистого Pixel 10. Бюджет — 0. Основна поверхня — компактний віджет головного екрана. Видимих сповіщень, звуку та вібрації немає. Заміна системної кнопки Google Home на екрані блокування не входить у проєкт.

Бажаний механізм отримання подій — webhook. Допустиму фактичну затримку потрібно оцінити на прототипі; гарантія миттєвості не узгоджена і технічно не підтверджена.

## 2. Перевірка автоматичного оновлення до основної розробки

Кандидат архітектури: HTTPS webhook → Cloudflare Worker на Free → актуалізація стану через API → звичайне FCM data-повідомлення → Android-віджет. Паралельна періодична перевірка API виявляє зміни загроз, яких немає у webhook, та відновлює стан після втрати подій.

Cloudflare Workers Free і Firebase Cloud Messaging розглядаються як кандидати, а не вже розгорнута інфраструктура. Безкоштовні квоти, ліміти CPU/зберігання, доступність потрібних облікових записів та роботу авторизації FCM слід перевірити перед вибором. Платний тариф і платіжні реквізити не підключати. При вичерпанні квот показувати недоступність/застарілість, а не автоматично переходити на оплату.

- [ ] Мінімальний Android-прототип на Kotlin: віджет, ручний запит API, приймання FCM data-only без повідомлень користувачеві.
- [ ] Перевірити звичайний пріоритет FCM. Не використовувати high priority для обходу обмежень тихих фонових оновлень.
- [ ] Виміряти час: стан джерела → сервер → телефон → перемальовування віджета.
- [ ] Перевірити активний телефон, тривалий сон/Doze, енергозбереження та перехід до головного екрана після розблокування.
- [ ] Перевірити потребу в одноразовому екрані налаштування для реєстрації пристрою. Не обіцяти відсутність будь-якого налаштування до перевірки життєвого циклу Android.
- [ ] Разом з власником оцінити фактичну свіжість перед основною реалізацією. Якщо вимогу не виконано, зафіксувати обмеження та погодити компроміс, не додавати нотифікації самовільно.

Webhook приймає сервер, не телефон. Він потребує токена провайдера. Навіть успішна доставка на сервер не означає, що телефон отримав або показав новий стан.

## 3. Модель стану та сервер

- `state == 0` — відбій лише після успішно перевіреної коректної відповіді.
- `state == 1` — активна тривога; аналізувати весь масив `causes`, не лише `last_cause`.
- Відомий червоний тип має пріоритет над жовтим. Мапінг затвердити за джерелом на етапі 1.
- Невідомий тип або порожні `causes` при активній тривозі — «Тривога: рівень не уточнено», а не відбій.
- Помилка запиту, невалідна відповідь, відсутність інтернету або протерміновані дані — явна ознака недоступності/застарілості.
- Розділити час події `created_at`, час успішного читання джерела та час отримання телефоном. Дата події не є датою перевірки.
- Визначити термін свіжості після експерименту. Відсутність нових подій сама по собі не підтверджує працездатність каналу.
- Зберігати останній відомий стан із позначкою його віку; не маскувати його під поточний після втрати зв'язку.

Сервер: перевірка автентичності webhook; повторне читання актуального стану, щоб дублікати або пізні події не повертали старий статус; послідовна обробка змін; обмеження запитів і backoff для 429/5xx; версія стану для захисту від застарілих push; захищена реєстрація одного пристрою й оновлення FCM-токена. Інтервал читання API обрати тільки після уточнення його лімітів. Невеликі повідомлення про свіжість/резервна синхронізація мають бути враховані в квотах.
